# A CI job holds secrets or a push token, or runs outside code, never both

Anything running in a GitHub Actions job can read every secret mapped into it, whichever step the secret is given to, and a job that runs npm packages or Gradle plugins runs code nobody here wrote. So the workflows that hold something worth stealing are split into jobs by what each holds, and the data passes between them as an artifact checked against hashes the first job wrote to its outputs (only that job can set them, so nothing else in the run can swap the files).

- **scrape.yml** (the weekly data): `scrape` has the feed and DataMall secrets and `TERMINUS_SCRAPE_TOKEN`, runs only this repo's standard-library Python, and can't push; `test` runs the npm dev dependencies with no secrets; `commit` can push and runs no npm code; `heartbeat` holds only `HC_SCRAPE_URL` and runs only curl. The data is compared with what's committed before any dependency is installed, so none can change the answer, and the suite gates the commit: a bad graph is worse than a stale one. The commit goes onto the exact commit that was scraped and tested, never rebased, which would put untested code under the new data.
- **android-deps.yml** (Dependabot's Gradle PRs): `generate` runs Gradle, and with it the new versions' plugin code, with a read-only token; `commit` holds `DEPS_TOKEN` (a Dependabot secret: a fine-grained token with Contents read and write on this repository only) and runs no Gradle. It pushes only the four dependency files, only when no hash already listed changed, every new one matches its repository's own checksum and no aapt2 jar is missing, and only onto the commit they were generated from. The checker is the branch's copy, set aside before the artifact arrives. It runs only for Dependabot's own pushes: Dependabot secrets reach only those runs, and its own push, made as the token's owner, doesn't start it again.
- **map-tiles.yml**: the R2 token is a secret of the `release` environment, which waits for a reviewer, so only a job that names it can read it, not every workflow, as a repository secret would allow. The build step downloads and cuts the map without it; the upload step, which downloads nothing, gets it.

A job that pushes does it the same way each time. The checkout keeps no token (`persist-credentials: false`), and the push step alone gets it, as an `http.extraheader` for that one command. `.git/config` is fingerprinted straight after checkout and checked again before the push, so nothing unpacked since (the artifact, say) can point the push elsewhere (a proxy, an `insteadOf`) or add a filter. git runs with no hooks and none of the runner's global or system config. The push is by commit hash and a fast-forward only: if the branch moved, GitHub refuses it, and the run says to run it again or leaves it to the newer push. The probe workflows' inputs are split unquoted into one argument per stop or service, so each must be a plain code that can't pass an option or a glob, checked again after `--` by the script.

Merging the jobs back into one would be simpler and was how the scrape started; so would trusting `actions/checkout`'s stored token. Both put the push token or the feed secrets in reach of every package in the lockfile.
