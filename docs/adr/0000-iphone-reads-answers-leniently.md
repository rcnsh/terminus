# The iPhone app reads answers leniently, on the server's clock

The server words every answer (ADR 0001), and it changes faster than apps update: a field is added, a list gains a kind this version doesn't know. A strict decoder fails the whole answer on one field it can't read, and every screen of every older version goes blank at once. So the iPhone app's answer types (`Sources/Shared/Answer.swift`, `Boards.swift`) require only what a screen can't do without. One element that doesn't decode is left out of its list (`Lossy`, `lenientList`), a whole number that comes as 95.5 is rounded (`lenientInt`), a card kind it doesn't know reads as `trip`, and a field it can't read is nil, never the whole answer with it. The exception is a journey whose bus is there but can't be read: that throws, so the app shows no journey rather than the wrong one (a walk). Because lenience would hide a part that stopped decoding, `GoldenTests` checks that every part each golden answer sends comes through. The answer's bytes are kept beside it (`NextAnswer.raw`) and sent with "Is this wrong?".

The profile is edited the same way: as JSON (`[String: Any]`), not a typed struct, so fields this version doesn't know survive a save. Every change goes through `Api.changeProfile`: read with its ETag, change, save with `If-Match`; on a 412 (another device, or another part of the app, saved in between) read again and make the change again, so a pin added on Stops never undoes a favourite added on the map. A class change made again finds its class where it moved to, never the one now at its old place. Settings carries the profile across actors as bytes, since a dictionary of `Any` isn't `Sendable`.

Times in answers (departures, leave-bys, `staleAt`) are the server's, and a phone clock a minute out would count them down a minute out. So the app learns the difference from the HTTP `Date` header of uncached API responses (`ServerClock`): only `no-store` ones, since a cached answer carries the time it was first sent; compared with the middle of when the request was sent and the answer came, plus half a second because `Date` drops its fraction; and ignored under 3 s, which is noise. Wherever a server time is compared with now, now is `ServerClock.now`. The Live Activity's and the widgets' own ticking times run on the phone's clock, so their ranges are moved by the skew, taken from one clock reading for both ends and never with an end before the start (`Text(timerInterval:)` can't take one). Times are shown in Singapore's zone whatever the phone's is set to, in the account's 12- or 24-hour choice (`Clock`, kept in the app group for the widgets), and written as the server's `clockMin` writes them ("6:36 PM", 下午 6:36), not in the phone's region's style ("6:36 pm" in British English), so a time the app writes matches the card's beside it.

We considered strict `Codable` types, which make a new field a crash or a blank screen for every older version, and the phone's own clock, which is wrong by however far the phone is out.
